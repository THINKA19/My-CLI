# 业务代码组织规范

本文说明本项目的业务代码怎么组织:按领域放进 `src/pages/` 下,各领域边界清晰、自成闭环。
本文是业务组织规范的完整说明；项目存在 `AGENTS.md` 摘要时，应与本文保持一致。

## 0. 定位与优先级

- 本项目基于 unibest 脚手架,脚手架自带规范在 `hermes/`,**不要修改它**。
- `hermes/` 管脚手架层面的事:生成物、条件编译、平台差异、分包、提交与发布。
- 本文只补充 hermes 没覆盖的部分:业务代码按领域怎么组织。
- 冲突时:脚手架层面的事以 hermes 为准;业务代码组织以本文为准。
- 新增页面的注册、分包、tabbar 等操作,仍按 `hermes/sop-new-page.md` 执行,本文只补充"领域目录"这一部分。
- 页面命名、SFC 结构、TS 约定等,仍按 `hermes/conventions.md`。

## 1. 设计目标

1. **上下文局部**:改一个功能时,相关代码集中在一个目录,人和 AI 读一个目录就能看全。
2. **改动范围可控**:每次改动能限定在某个领域内,不容易误伤其他模块。
3. **边界清晰**:领域之间只通过明确的公共入口交互,内部可以自由重构。
4. **便于并行与删除**:不同领域并行开发冲突少;删除功能就是删除一个目录。
5. **新手友好**:规则少、命名直白、跟着框架约定走;复杂度按需长出来,不提前设计。

## 2. 为什么按领域,而不是按技术层

按技术层(所有接口一个目录、所有组件一个目录、所有状态一个目录)的问题:一个需求的代码分散在多处,AI 容易漏文件、读进无关内容;多人同时改同一批公共文件,冲突多;删除功能容易留残余。

按领域组织后,"订单"相关的接口、组件、逻辑、类型都在订单目录内,需求边界和目录边界一致。分层思想没有消失,只是下沉到每个领域内部:领域内部仍然保持 UI、逻辑、数据分离。

**不另建 `features/` 目录:** uni-app 约定页面放 `pages/`。在五个顶层分类下完整保留业务领域，页面和该领域的业务代码在同一处。

分类目录为 `home`、`ordering`、`queue`、`pickup`、`account`，业务分类最多三层。分类层不新增 `index.ts` 或页面；每个分类的默认首页统一放在 `index/index.vue`，其组件、逻辑和资料放在同一个 `index/` 领域目录内。其他领域保留业务名称；`pickup/index` 承载取餐首页，`pickup/order-details` 承载订单详情、扫码结果和评价。

## 3. 目录结构

### 3.1 顶层补充架构

这里只说明项目补充的公共能力、基础设施与应用组装结构。脚手架已有的入口、静态资源、样式、国际化及配置目录沿用原有规范，不在此重复展开。业务领域目录见 3.2 节。

```
src/
├─ shared/                     无具体业务归属的通用代码
│  ├─ components/              通用 UI
│  ├─ hooks/                   通用响应式能力
│  └─ utils/                   通用纯工具函数
│
├─ infrastructure/             基础设施
│  ├─ http/                    保留现有请求客户端结构
│  ├─ logging/                 按需：日志采集与上报
│  ├─ storage/                 按需：通用存储读写
│  └─ platform/                按需：平台 API 适配
│
└─ app/                        应用级启动与组装
   ├─ lifecycle.ts             启动、前后台流程、重试与监听管理
   └─ tabbar.ts                保留现有底部导航配置
```

**职责与归属：**

- `shared/` 不拥有具体业务规则。领域专属组件、类型、状态和逻辑仍留在领域内，不因多个页面使用就自动提升。
- `shared/hooks/` 封装通用响应式能力；领域内 `composables/` 封装业务响应式逻辑。两者是项目的命名分工，不是不同技术机制。普通纯函数放 `utils/`，不混入 hooks。
- `infrastructure/` 封装网络、存储及平台等外部能力。HTTP 沿用现有实现，不另建顶层或 shared 下的请求客户端。
- 基础设施的 `storage/` 负责怎样读写；领域的 `storage/` 决定缓存什么、何时失效及如何清理。
- `platform/` 按需封装更新检查、网络监听等平台操作；已有同类实现应复用，避免同时维护两套。
- `app/` 决定应用启动、进入前台时的执行顺序，并连接领域与基础设施。它调用领域公开能力，不承载订单计算、用户资料等具体业务规则。
- 当前能力注册较少，放在 `lifecycle.ts` 内职责明确的函数中即可。只有注册工作明显复杂、需要独立维护时，才按需拆出 `registrations.ts`；不作为必建文件。
- 生命周期的必要初始化、降级、监听释放及页面就绪契约见 app/README.md（项目根目录：`src/app/README.md`）。配置状态由 settings store 唯一持有，app 只负责组装与编排。

**依赖边界：** 业务领域可以使用 shared 与 infrastructure；这两类基础能力不得反向依赖领域。app 作为应用组装层，可以使用领域的 `index.ts` 和基础设施公开入口。例如由 app 注册 token 获取函数，HTTP 不直接导入用户领域。

**落实方式：** 此树是目标职责结构，不要求立刻创建全部目录。原有脚手架目录不搬动；已有目录沿用，缺失能力按真实需求建立。存量项目代码归位按明确任务逐步执行，不因补充本文擅自进行代码迁移或重复建设。

### 3.2 领域目录

```
src/pages/account/orders/order/
├─ index.vue             页面入口
├─ api/                  业务接口
│  ├─ endpoints.ts       后端接口路径清单
│  └─ ...
├─ components/           领域专属 UI
├─ composables/          响应式逻辑
├─ models/               类型、枚举、转换函数
├─ index.ts              对外公共入口
├─ README.md             领域职责与使用说明
├─ docs/                 后端与业务参考
│  └─ db.md              数据表、字段含义及接口参数说明
├─ storage/              按需：持久化
├─ domain/               按需：复杂纯业务规则
└─ adapters/             按需：跨领域适配
```

**识别规则只有一条:领域目录根下的 `.vue` 是页面,子目录是该领域的内部实现。**

页面文件的命名与注册按 hermes 的约定。

### 3.3 复杂度分级

- 每个业务领域：`index.ts`、`README.md`、`docs/db.md`；`api/ components/ composables/ models/` 按实际代码职责建立。
- 中等领域:有持久化需求时再加 `storage/`；共享响应式状态可以使用领域根部 `store.ts`，它不等于持久化目录。
- 复杂领域(少数):再加 `domain/`、`adapters/`

**文档是必备项，代码目录按需创建。** 聚合页面通过所属领域的公共入口取数，在 db.md 链接数据所有者；不为了统一目录复制 API 或建立空目录。无需独立复杂业务规则时不建 `domain/`。

## 4. 前置条件:页面扫描要排除领域内部目录

脚手架通过配置生成路由(`pages.config.ts` 等,具体机制以 hermes 为准)。如果路由生成会扫描 `src/pages/` 下**所有** `.vue` 文件,那么领域内部 `components/` 里的组件可能被误当成页面注册。

- 在新增第一个领域之前,先确认扫描规则已排除各领域的内部目录(`api/`、`components/`、`composables/`、`models/`、`domain/`、`adapters/`、`storage/`、`docs/`)。
- 如果无法排除,则领域专属组件不要放在 `src/pages/` 下,改放脚手架公共的组件目录,并用领域名做前缀或子目录区分。
- 此项以实际验证为准:新增后检查生成的 `pages.json` 里没有出现组件路径。

## 5. 各目录职责

### 5.1 api/:接口

- 默认包含 `endpoints.ts`(路径清单)和接口函数文件。
- 接口函数调用 http 请求客户端(见 [HTTP 规范](./http.md)),不自己创建请求配置。
- 后端返回的数据在这里通过 `models/` 的转换函数变成前端结构。
- **接口手写、明确**:每个接口都清楚写出路径和参数,不使用按资源自动生成增删改查的工厂。原因:后端接口路径和参数各不相同,自动生成的抽象会不断出现例外,新手和 AI 都更难读懂。可以通用的只有 loading、错误、分页这类状态管理,放在公共的 hooks。

### 5.2 endpoints.ts:路径清单

为什么单独一个文件:接口函数多了,路径散在各函数里很容易看混;集中后一个文件就能看全这个领域用了哪些后端接口,方便对照后端文档,路径变化只改一处。

约定:
- 每个领域一个 `endpoints.ts`,位于该领域的 `api/` 下,所有领域保持一致。
- 一个领域一个对象,键名用动作命名(如 list、detail、remove),不用路径本身当名字。
- 每条路径后用一行注释说明用途;有特殊网关时在这里标明,调用方不用再记。
- 只放路径和网关信息,不放参数和逻辑。
- 接口函数、composables、组件中**禁止直接写路径字符串**。
- 不叫 `route.ts`,避免与前端页面路由混淆。
- 不做全项目统一的路径总文件:全局总文件会回到按技术层集中的老问题,多人修改易冲突,删除领域时易漏清理。
- 公共会话路径由 `shared/session/api/endpoints.ts` 拥有，媒体路径由 `shared/media/api/endpoints.ts` 拥有；上传继续使用既有请求客户端公开能力。普通业务迁移不修改请求客户端。

### 5.3 components/:领域专属组件

只负责展示和交互,不直接写请求和复杂业务逻辑。被多个领域使用的组件,提升到公共组件目录。

### 5.4 composables/:响应式逻辑

承载 UI 与逻辑分离:加载列表、分页、表单状态、提交流程、loading 与错误状态等。组件和页面通过调用 composable 获得数据和方法。

### 5.5 models/:数据词典

包含:
- 枚举和常量(把状态码等魔法数字变成有名字的东西,并提供显示文案)
- 后端原始数据结构(与后端字段一一对应)
- 前端实际使用的数据结构
- 从后端结构到前端结构的转换函数

`models/` 在领域内依赖链最底层,**不引用领域内任何其他目录**,因此不会产生循环依赖。

### 5.6 index.ts:公共入口

领域对外的"合同"。
- 只导出外部确实需要的接口、类型、组件、逻辑。
- 不使用 `export *`,否则边界形同虚设。
- 导出越少越好;导出很多说明该领域与其他领域纠缠过深。
- 页面 `.vue` 文件不通过它导出,也不被任何代码 import(页面只由路由使用)。

### 5.7 README.md:模块说明(必备)

很短:这个领域做什么、对外导出什么、依赖哪些其他领域、有哪些需要注意的业务规则。AI 进入领域时先读它。

### 5.8 按需目录

- **storage/**:该领域有专属持久化需求(本地缓存、草稿)时建,把存储操作集中起来。
- **domain/**:复杂的纯业务规则(价格计算、优惠叠加、状态流转、权限判断)。判断标准:能否不引入前端框架就运行?能、且有一定复杂度才放这里;只是"请求数据、存入响应式变量、控制 loading"就放 composables。满足任一条再建:规则复杂到 composable 写不下;需要脱离框架做单元测试;同一规则被多处复用。
- **adapters/**:防腐层,只有本领域需要调用其他领域时才建,详见第 7 节。
- **docs/**:每个领域必备 `db.md`，即使暂未取得真实表结构，也要记录已知接口语义和待确认项；详见第 8 节。

## 6. 依赖规则

### 6.1 总体方向

```
路由/页面  →  各领域(通过 index.ts)  →  公共目录与请求客户端
```

- shared、infrastructure 等公共基础能力和请求客户端**不得依赖任何领域**；app 是应用组装层，可以通过领域的 `index.ts` 使用公开能力。
- 领域之间只能通过对方的 `index.ts` 引用,不得引用内部文件。
- 领域之间不得循环引用。

### 6.2 领域内部

```
页面 → components → composables → api → models
                        ↓
                  domain / storage → models
```

- composables 可以使用 api、domain、storage;组件使用 composables,不绕过它直接调接口。
- 同一领域内部可以用相对路径互相引用。

### 6.3 先放局部,再提升

新代码先放在使用它的领域内。第二个领域真正需要时,才提升到公共目录。过早抽象的代价比少量重复更大。

### 6.4 页面保持很薄

页面只负责:调用领域的 composables、把组件组装起来、处理页面级的生命周期和导航。不直接调接口,不写复杂业务逻辑。

## 7. 跨领域引用

跨领域引用无法完全消除,目标是让它可控。要防两种风险:
- **编译期耦合**:被依赖方改接口,依赖方大面积出错。
- **运行期耦合**:被依赖方接口故障,依赖方页面跟着崩。

按优先级处理:

1. **最好不发生引用——在页面里组装。** UI 需要别的领域的数据时,由页面分别使用两个领域,再通过属性或插槽把数据传给组件。页面本来就属于"最上层",可以同时引用多个领域的 `index.ts`。
2. **让后端聚合。** 订单页每次都要用户名,最彻底的办法是订单接口直接返回,或后端提供聚合接口。前端少一次请求,也不用跨领域取数。
3. **多个领域都要的内容提升出去。** 例如当前登录用户,放入公共的 store 或会话管理,不属于任何业务领域。
4. **业务逻辑跨领域时，只引用对方的公共入口。** 简单调用不额外建立转发层；当外部模型不稳定、确实需要转换或替换实现时，再建立 `adapters/`，以本领域需要的最小数据结构隔离变化。禁止循环依赖。
5. **事件通知(慎用)。** 只用于"通知类"场景,例如退出登录后清理缓存;不要用来取数据,因为调用链不透明,人和 AI 都难追踪。

**运行期降级:** 跨领域的次要数据加载失败时,不应拖垮主体内容。并行请求时使用"各自返回成功或失败"的方式,而不是"一个失败全部失败";次要区域失败时显示兜底提示,主体照常展示。

## 8. 领域内 docs/:后端参考文档

### 8.1 目的

前端调用接口时通常只看到几个参数,不知道背后是哪张表、字段含义、哪些必填、状态值每个数字代表什么、金额单位是什么、删除是否软删除。这些在代码里看不出来,却是 AI 最容易写错的地方。领域内 `docs/` 用来补充这类后端与业务背景。

### 8.2 约定

- 仅供参考,**不参与代码运行,不被任何代码引用**。
- 与代码或后端实际返回冲突时,以代码和后端实际返回为准。
- 文档开头标注来源与参考时间,例如"来源于后端某服务、某年某月,仅供参考"。
- 只写稳定信息:表名、字段含义、枚举值、业务规则、接口与表的对应。不写易变的细节(索引、存储引擎等)。
- 只写前端用到的内容,没用到的字段标注一下即可。
- 如果后端有接口文档或可生成类型的工具,优先用它们生成类型,本文档只补充"业务含义"。
- 每个领域维护一个 `docs/db.md`；表很多时再拆成 `docs/db/<已核实表名>.md`，保留 db.md 总入口。
- 未取得后端源码、DDL 或权威资料时，真实表名、SQL 类型、默认值、事务、权限、软删除和幂等全部标记待确认，不能从请求参数反推为事实。
- 区分数据库字段、接口 DTO 和前端派生字段；TypeScript 可选属性不等于 SQL 可空，金额/时间等单位必须注明依据。
- 聚合页面没有独立表时，写明数据所有者并链接其 db.md，不复制维护多份字段事实。
- 文档与接口/模型改动同时维护；不包含实际凭证、个人资料或生产样本。

### 8.3 推荐内容

1. 本领域涉及的表及其关系。
2. 每张表的字段说明:字段名、类型、含义、枚举值、单位、是否软删除。
3. 业务规则:状态流转限制、哪些字段允许修改等。
4. 接口与表的对应:哪个接口读写哪张表,哪些字段可改；未确认的映射明确标记。
5. 操作效果与副作用：取消、删除、支付、退款等是否连带更改库存/资产/权益，哪些已经证实、哪些仍待后端确认。

### 8.4 与 endpoints.ts、models/ 的关系

| 文件          | 回答的问题                           | 是否参与运行 |
| ------------- | ------------------------------------ | ------------ |
| endpoints.ts  | 这个领域调了哪些后端接口             | 是           |
| docs/db.md    | 每个接口背后是哪张表、字段什么含义   | 否           |
| models/       | 前端实际使用的类型、枚举、转换       | 是           |

工作流程:先读 docs 理解后端,再在 models 里写出前端要用的类型和枚举。

## 9. 页面写法

- **默认直接编写 Vue 页面。** AI 对标准写法最熟练;出问题可以直接断点调试;不会被自定义配置语言限制。
- **配置式只用在高度重复的 CRUD 场景**(列表加筛选加新增编辑,十几个页面结构几乎一致):封装成组件,列和字段用配置描述,页面本身仍是 Vue 文件,特殊逻辑通过插槽扩展。
- 不要自创复杂的页面配置语言,它往往越做越复杂,最后变成难以维护的半成品编程语言。
- 平台差异的处理按 hermes:只用条件编译。

## 10. 命名与粒度

- 领域目录用小写英文单词,单数形式,例如 user、order。
- 目录内文件粒度保持一致:选择"一个接口一个文件"或"一个领域一个接口文件"其中一种,所有领域统一,不要混用。
- 小领域不要过度拆分。
- 每个领域结构同构,AI 看过一个就能仿写新的。

## 11. 新建领域的流程

1. 在 `src/pages/` 对应分类或分组下创建领域目录,只建实际需要的目录和文件。
2. 确认页面扫描已排除领域内部目录(见第 4 节)。
3. 在 `models/` 中定义类型、枚举、转换函数;若有后端参考资料,先写进 `docs/`。
4. 在 `api/endpoints.ts` 登记后端路径(含网关和用途注释)。
5. 在 `api/` 中编写接口函数,只引用 endpoints,调用 http 请求客户端。
6. 在 `composables/` 中写响应式逻辑,在 `components/` 中写专属 UI。
7. 在领域根目录写页面,保持很薄。
8. 在 `index.ts` 中导出外部需要的内容,保持克制。
9. 编写 `README.md` 和 `docs/db.md`；缺少后端结构资料时先记录已知前端契约与待确认事项。
10. 页面注册、分包、tabbar 等按 `hermes/sop-new-page.md` 执行。

## 12. 删除与重构

- **删除功能**:删除整个领域目录,再清理路由配置和其他位置对它的引用。
- **重构领域内部**:保持 `index.ts` 的名称、类型、返回值、错误、副作用和时序契约；仅导出名称不变不能证明外部不受影响，需检查消费者并验证兼容性。
- **拆分领域**:一个领域过大、内部出现明显两块独立业务时再拆,不要一开始切得过细。
- **提升到公共目录**:确认第二个领域真正需要时再做。
- **分包**:领域目录边界不自动等于实际分包边界，分包规则按 hermes 和真实构建配置执行。

## 13. 自动化约束

业务规则、接口契约与共享状态测试放在其所属模块的 `__tests__/` 中，不设 `src/__tests__/` 集中目录。混合多个领域的测试按断言实际归属拆开；跨领域流程的测试由流程拥有者管理。`pnpm test:run` 仅运行这些测试。重构阶段的临时架构检查脚本已撤下，以下边界通过代码检查维护；将来有实际需要时再引入自动检查：

1. 外部只能引用领域的 `index.ts`。
2. 公共目录不得引用 `src/pages/`。
3. 领域内 `models/` 不得引用领域内其他目录。
4. 禁止领域之间循环引用。
5. 禁止领域 `index.ts` 使用 `export *`。

规则报错时,应调整代码结构,而不是关闭规则。"接口函数中不写路径字符串"目前主要靠本文约定和代码评审,必要时可补自定义检查规则。

## 14. 何时调整本规范

- 项目规模很小:可退回简单分层,不必强行领域化。
- 某个按需目录在多个领域中反复出现:可考虑改为默认目录。
- 某个默认目录在大多数领域中都是空的:可考虑改为按需目录。
- 领域目录整体变得太杂:只要 `index.ts` 边界守得住,可以整体搬出 `pages/`,代价不大。
- 调整后同步更新本文、`AGENTS.md` 和 ESLint 规则。

## 附:规则速查

1. 领域目录根下的 `.vue` 是页面,子目录是内部实现。
2. 领域之间只通过 `index.ts` 引用,不循环引用,不 import 页面 `.vue`。
3. 公共目录不依赖任何领域。
4. 接口路径登记在 `api/endpoints.ts`,其他地方不写路径字符串。
5. 接口手写,不用 CRUD 工厂。
6. 数据转换写在 `models/`,由 `api/` 调用。
7. 页面保持很薄,不直接调接口。
8. 新建领域只建默认目录;其余按需。
9. 先放局部,第二个领域需要时再提升。
10. 领域内 `docs/` 仅供参考,冲突时以代码和后端实际返回为准。
