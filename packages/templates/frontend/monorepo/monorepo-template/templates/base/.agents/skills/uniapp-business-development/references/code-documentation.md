# 代码注释规范

## 🎯 核心目标
在任何生成、修改或重构代码的场景下，你必须**严格强制**输出符合企业级架构标准的 JSDoc 注释。拒绝提供任何无注释、注释敷衍或格式不规范的“裸代码”。所有代码的注释结构必须严格遵循下述规范。

## 📜 核心约束规则 (Core Rules)

### 1. 强制文件级顶部注释 (File-Level Header Annotation)
每个新建或输出的核心代码文件，必须在文件第 1 行包含一个标准的块级全局注释，结构必须使用 `=====` 包裹，并严格包含以下三大模块：
*   **【文件概述】**：清晰说明该文件在系统架构中的位置（如 Shared Kernel, Infrastructure, Services 等），以及它的核心职责与特性。
*   **【方法与导出清单】**：以列表形式枚举该文件导出的所有核心 API（函数、类、接口），并用简炼的语言说明其作用。
*   **【综合使用示例】**：必须提供一段完整的、带有 `import` 语句的真实业务侧调用代码示范。

### 2. 强制方法/函数级注释 (Method-Level Annotation)
所有导出的函数、类、接口、类型别名，上方必须紧贴标准的 JSDoc 注释，必须包含以下要素：
*   **功能简述**：一句话概括方法作用。
*   **`@param`**：详细说明每个入参的名称、数据类型及其业务含义（如果是配置对象，需简述关键属性）。
*   **`@returns`**：明确说明返回值的结构或具体含义。
*   **`@example`**：必须提供至少 1~2 个具体的调用代码及预期输出结果（`// => result`）。

## 💡 标准模板参考 (Templates)

在生成注释时，必须严格对齐以下参考模板的缩进、排版与视觉风格：

### 模板 A：文件顶部全局注释模板
````typescript
/**
 * ============================================================================
 * [模块中文名称] ([Module English Name])
 * ============================================================================
 *
 * 【文件概述】
 * 本文件处于系统架构的 [架构层级]（如 Shared Kernel），主要负责处理 [核心业务逻辑]。
 * 严禁向上依赖任何上层模块。
 * 
 * 核心特性：
 * 1. [特性1]：详细说明...
 * 2. [特性2]：详细说明...
 *
 * 【方法与导出清单】
 * - methodName1(arg)      : [简要说明方法1的作用]
 * - ClassName             : [简要说明类的主体功能]
 *
 * 【综合使用示例】
 * ```typescript
 * import { methodName1 } from '@/path/to/module'
 * 
 * // 场景 A：具体业务场景描述
 * const result = methodName1(args) // => [预期结果]
 * ```
 * ============================================================================
 */
````

### 模板 B：方法级 JSDoc 注释模板

```typescript
/**
 * [方法功能一句话描述]
 * [（可选）补充说明该方法的特殊逻辑、边界情况或注意事项]
 *
 * @param [参数名] [参数业务含义描述]
 * @param [参数名2] [参数业务含义描述]
 * @returns [返回值具体含义与结构描述]
 *
 * @example
 * [方法名]([测试参数1]) // => [预期输出结果]
 * [方法名]([测试参数2]) // => [预期输出结果]
 */
export function exampleFunction(param1: any, param2?: any): any {
  // implementation...
}
```

## ⚠️ 执行指令 (Execution Trigger)

每当用户要求你“写一段代码”、“封装一个方法”或“新建一个文件”时，你必须在脑海中首先应用上述模板，**宁可牺牲代码生成的长度，也绝对不省略上述注释结构**。如果代码包含多个复杂方法，每一个都必须配齐完整的 `@param`、`@returns` 和 `@example`。

## 语法适配与维护要求

- 上述顶部三部分、方法说明、参数、返回与示例要求属于强制规范，不得以精简、避免重复或方法简单为由改成可选。
- TS/JS 核心文件使用顶部块注释。保留必须在前的 shebang、许可证或指令；Vue 按 SFC 语法在顶部使用合法注释承载同样三部分，方法 JSDoc 放在 script 中。JSON 等不允许注释的文件使用同名配套说明，不写入非法注释。
- 函数按实际参数填写 @param，说明类型、业务含义和单位；无参数时写明“无参数”，不编造参数。无返回值时 @returns 写明 void 及副作用；异步返回说明 Promise 的结果与失败条件。
- 导出类、接口与类型别名同样必须有紧贴声明的说明和示例。类说明构造参数、实例职责和公开方法；接口与类型说明字段约束及赋值示例。没有调用签名时用对应结构说明输入与值的含义，不伪造函数参数或返回值。
- 顶部导出清单、import 示例、方法示例与实际代码同步更新。模板占位符必须替换；预期输出需有依据，异步外部结果说明条件，不编造生产响应。
- 原规范定义文件顶部注释与方法/导出声明上方注释，未规定额外的文件底部注释。不得自行增加一套未确认的尾部模板。
